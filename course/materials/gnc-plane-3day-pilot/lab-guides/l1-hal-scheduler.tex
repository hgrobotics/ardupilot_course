\section*{Lab summary for the instructor}

\textbf{Learning objective:} The engineer can attach gdb to a live ArduPilot SITL process, resolve \texttt{Plane::ahrs\_update}, read \texttt{AP\_HAL::millis()} and \texttt{AP::scheduler().get\_loop\_rate\_hz()}, and explain where these values come from in the source tree.

\textbf{Depth:} internals --- this is a code-walk lab, not a flight lab. The plane never arms or takes off.

\textbf{Feed-forward:} The scheduler probe here prepares for M5 (parameter persistence), M7 (EKF lane switch), and M8 (gain modify). Engineers who understand that the scheduler loop is a real, inspectable C++ call graph will reason correctly about timing in later labs.

\section*{Pre-arm setup checklist}

\begin{itemize}[label={[ ]}]
  \item Confirm \texttt{build/sitl/bin/arduplane} exists and shows a recent modification time.
  \item Confirm it was built with debug symbols: \texttt{gdb build/sitl/bin/arduplane -ex 'info symbol main' -ex quit} should resolve \texttt{main}.
  \item Confirm \texttt{gdb} is installed: \texttt{gdb --version}.
  \item For the student-facing path (interactive \texttt{gdb -p <pid>}), confirm ptrace is allowed: \texttt{cat /proc/sys/kernel/yama/ptrace\_scope} should be \texttt{0}. If \texttt{1} or higher, run \texttt{echo 0 | sudo tee /proc/sys/kernel/yama/ptrace\_scope}. (The headless harness path does not need this --- it launches arduplane as a gdb child.)
  \item Projector / shared screen should show the source file \codepath{ArduPlane/Plane.cpp} around line 167 (\texttt{void Plane::ahrs\_update()} body starts at line 167; declaration header is at 165). See \citerange{ArduPlane/Plane.cpp}{165}{200}.
  \item Confirm the repo is on branch \texttt{GNC-0.1}: \texttt{git rev-parse --abbrev-ref HEAD}.
\end{itemize}

\section*{What you will do}

In this lab you will attach the GNU debugger to a running ArduPlane SITL process and read two live values straight out of the flight-control loop: the HAL monotonic clock (\texttt{AP\_HAL::millis()}) and the active scheduler loop rate (\texttt{AP::scheduler().get\_loop\_rate\_hz()}).

This is not a flying lab --- the plane does not take off. The goal is to confirm that the Hardware Abstraction Layer (HAL) is a real, callable interface, not just documentation, and that the scheduler truly runs at 50 Hz for a fixed-wing vehicle. After this lab you will have a mental model of how ArduPilot maps ``main loop tick'' to the HAL clock --- a skill you will build on in every subsequent lab.

\section*{Before you start}

\begin{itemize}
  \item You must have completed the build step from Module M3: \texttt{./waf configure --board sitl --debug \&\& ./waf plane}. Confirm \codepath{build/sitl/bin/arduplane} exists and was built recently.
  \item \texttt{gdb} must be installed. Verify: \texttt{gdb --version}.
  \item Open two terminal windows side by side, both \texttt{cd}'d to the repository root.
  \item No MAVProxy, GCS, or display server needed for this lab.
\end{itemize}

\section*{The steps}

\subsection*{Step 1 --- Build the debug binary (if not already built)}
\begin{Verbatim}[frame=single,fontsize=\small]
./waf configure --board sitl --debug
./waf plane
\end{Verbatim}

\subsection*{Step 2 --- Start SITL without MAVProxy}
In Terminal A:
\begin{Verbatim}[frame=single,fontsize=\small]
Tools/autotest/sim_vehicle.py -v ArduPlane -f plane --debug --no-mavproxy
\end{Verbatim}
Leave this terminal running.

\subsection*{Step 3 --- Find the process ID}
In Terminal B:
\begin{Verbatim}[frame=single,fontsize=\small]
pgrep arduplane
\end{Verbatim}
Note the number printed (e.g. \texttt{12345}).

\subsection*{Step 4 --- Attach gdb}
In Terminal B:
\begin{Verbatim}[frame=single,fontsize=\small]
gdb build/sitl/bin/arduplane -p $(pgrep arduplane)
\end{Verbatim}

\subsection*{Step 5 --- Set a breakpoint on the HAL update function}
\begin{Verbatim}[frame=single,fontsize=\small]
(gdb) b Plane::ahrs_update
\end{Verbatim}
Expect: \texttt{Breakpoint 1 at 0x...: file ArduPlane/Plane.cpp, line 167.}

\subsection*{Step 6 --- Continue until the breakpoint fires}
\begin{Verbatim}[frame=single,fontsize=\small]
(gdb) c
\end{Verbatim}
Within a second or two (function runs at 50 Hz), gdb prints \texttt{Breakpoint 1, Plane::ahrs\_update}.

\subsection*{Step 7 --- Read the HAL clock}
\begin{Verbatim}[frame=single,fontsize=\small]
(gdb) print AP_HAL::millis()
\end{Verbatim}
Expect a positive integer (\texttt{\$1 = 3471} or similar).

\subsection*{Step 8 --- Read the scheduler loop rate}
\begin{Verbatim}[frame=single,fontsize=\small]
(gdb) print AP::scheduler().get_loop_rate_hz()
\end{Verbatim}
Expect \texttt{\$2 = 50}. This is the plane default at \citeline{libraries/AP\_Scheduler/AP\_Scheduler.cpp}{46}.

\subsection*{Step 9 --- Detach and quit}
\begin{Verbatim}[frame=single,fontsize=\small]
(gdb) detach
(gdb) quit
\end{Verbatim}

\subsection*{Step 10 --- Stop SITL}
Switch to Terminal A and press \texttt{Ctrl-C}.

\section*{What success looks like}
\begin{itemize}
  \item gdb resolves the breakpoint at \codepath{ArduPlane/Plane.cpp} (line $\sim$167).
  \item After \texttt{c}, gdb stops and prints \texttt{Breakpoint 1, Plane::ahrs\_update}.
  \item \texttt{print AP\_HAL::millis()} prints a positive integer.
  \item \texttt{print AP::scheduler().get\_loop\_rate\_hz()} prints \texttt{50}.
\end{itemize}

If you see \texttt{no symbol "Plane::ahrs\_update" in current context}, the binary was not built with debug symbols. Go back to Step 1 and make sure you used \texttt{--debug} in the configure step.

If \texttt{print AP\_HAL::millis()} prints \texttt{0}, gdb evaluated the function in a context where the HAL is not yet live. Let the breakpoint fire once more with another \texttt{c}, then try again.

\section*{Common mistakes and quick fixes}

\begin{enumerate}
  \item \textbf{``no symbol Plane::ahrs\_update''} --- you forgot \texttt{--debug} in \texttt{./waf configure}. Re-run \texttt{./waf configure --board sitl --debug \&\& ./waf plane} and restart.
  \item \textbf{gdb attaches but immediately shows a stopped state (SIGSTOP)} --- normal; SITL is paused while gdb attaches. Type \texttt{c} to resume.
  \item \textbf{pgrep prints nothing} --- SITL is not running. Switch to Terminal A and check it started. If \texttt{sim\_vehicle.py} is still building, wait for the \texttt{Starting} message before running pgrep.
  \item \textbf{gdb says ``ptrace: Operation not permitted''} --- run \texttt{echo 0 | sudo tee /proc/sys/kernel/yama/ptrace\_scope}, then retry the gdb attach.
  \item \textbf{Breakpoint fires too fast and gdb floods the screen} --- type \texttt{(gdb) c 1} to single-step through one invocation, take your readings, then detach.
\end{enumerate}
