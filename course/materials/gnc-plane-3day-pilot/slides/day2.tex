\section{Module M5 --- Core Infrastructure (2.0 h, internals)}

\begin{frame}{Module M5 --- Core Infrastructure Libraries with \texttt{AP\_Param} adoption emphasis}
  \textbf{2.0 h, lecture+code-walk+lab, \emph{internals} depth.}\\[1ex]
  \texttt{AP\_Param}, \texttt{AP\_Scheduler}, \texttt{AP\_Logger} are the three libraries that ``come with'' everything else when you extract.
  \vfill
  Learning objectives:
  \begin{enumerate}
    \item Read \texttt{AP\_Scheduler::Task} and \texttt{Plane::scheduler\_tasks[]}. Recognise \texttt{FAST\_TASK} vs \texttt{SCHED\_TASK(rate\_hz, max\_time\_us, priority)}.
    \item Read the \texttt{AP\_GROUPINFO} family --- \texttt{var\_info[]} maps to EEPROM with full \texttt{@Param}/\texttt{@Range}/\texttt{@User} annotations.
    \item Read \texttt{AP\_Logger}'s \texttt{WriteV}/\texttt{Write} API; recognise the \texttt{LogStructure} registration.
    \item Read \texttt{AP\_Vehicle} and how \texttt{Plane : public AP\_Vehicle} consumes the framework.
  \end{enumerate}
\end{frame}

\begin{frame}{The scheduler table revisited --- \emph{at code level}}
  \begin{itemize}
    \item \citerange{ArduPlane/Plane.cpp}{30}{60} --- \texttt{SCHED\_TASK} and \texttt{FAST\_TASK} macro definitions.
    \item \citerange{ArduPlane/Plane.cpp}{62}{95} --- the table itself (we saw this at survey in M1; now we read it).
  \end{itemize}
  \vfill
  Two macros build entries:
  \begin{itemize}
    \item \texttt{FAST\_TASK(func)} --- runs every fast-loop tick (50 Hz for plane).
    \item \texttt{SCHED\_TASK(func, rate\_hz, max\_time\_us, priority)} --- rate-limited.
  \end{itemize}
  \vfill
  Fields \texttt{rate\_hz} and \texttt{max\_time\_us} are advisory: the cooperative scheduler will skip a task on a given tick if the budget is tight. \textbf{There is no pre-emption.} A task that overruns silently steals time from the next tick.
\end{frame}

\begin{frame}[allowframebreaks]{Trade-off you must internalise --- cooperative scheduler}
  \begin{quote}
    Simple, predictable, \emph{and unforgiving}.
  \end{quote}
  \vfill
  A 50 ms task overrun is silent --- there is no pre-emptive watchdog above the task layer.
  \vfill
  Compare to your stack:
  \begin{itemize}
    \item Pre-emptive RTOS guarantees deadlines but adds context-switch cost and lock-contention surface.
    \item ArduPilot's cooperative model trades that determinism for simplicity and inspectability. The bug class shifts from ``deadlock'' to ``silent overrun.''
  \end{itemize}
  \vfill
  Loop-rate accessors you will use in L1 / elsewhere: \citerange{libraries/AP\_Scheduler/AP\_Scheduler.h}{140}{180} --- \texttt{get\_loop\_rate\_hz()}, \texttt{get\_loop\_period\_us()}, \texttt{get\_loop\_period\_s()}.
  \instfaq{How is overrun detected at all?}{Logged in \texttt{PM} message; not actionable mid-flight. Diagnosed offline. M9 covers log layout.}
\end{frame}

\begin{frame}{The parameter system --- \texttt{AP\_GROUPINFO} family}
  \begin{itemize}
    \item \citerange{libraries/AP\_Param/AP\_Param.h}{140}{160} --- \texttt{AP\_GROUPINFO}, \texttt{AP\_GROUPINFO\_FLAGS}, \texttt{AP\_GROUPINFO\_FRAME}, \texttt{AP\_GROUPINFO\_FLAGS\_DEFAULT\_POINTER}.
  \end{itemize}
  \vfill
  All expand into a \texttt{GroupInfo} struct entry carrying:
  \begin{itemize}
    \item Short name ($\leq$ 16 chars).
    \item Index.
    \item Class+member offset.
    \item Default value.
    \item Type.
  \end{itemize}
  \vfill
  The full \texttt{@Param} comment block is parsed by an offline tool to produce the parameter manifests GCSes consume. Self-documenting at the source.
\end{frame}

  \end{Verbatim}
  \vfill

\begin{frame}[allowframebreaks]{The hard rule --- \emph{never renumber} \texttt{AP\_GROUPINFO} indices}
  \begin{quote}
    The index is baked into stored user configs in EEPROM/SD. Renumbering an existing index silently corrupts user parameter sets across firmware upgrade.
  \end{quote}
  \vfill
  \textbf{Only append new entries at unused indices.}
  \vfill
  This is the constraint your fleet-migration story has to honour, not a recommendation.
  \instnote{When an engineer asks about migration patterns: stale-but-correct values are preferable to fresh-but-corrupted ones. The downstream adoption module returns to this in the \texttt{AP\_Param} extraction discussion.}
\end{frame}

\begin{frame}{The setup $\rightarrow$ load\_all $\rightarrow$ save lifecycle}
  \begin{itemize}
    \item \citerange{libraries/AP\_Param/AP\_Param.cpp}{355}{400} --- \texttt{AP\_Param::setup()}: walks the registered top-level table, prepares the in-memory parameter graph.
    \item \citerange{libraries/AP\_Param/AP\_Param.cpp}{1555}{1620} --- \texttt{AP\_Param::load\_all()}: reads stored values out of the EEPROM/Storage backend at boot.
  \end{itemize}
  \vfill
  Saves are deferred and batched. From outside the library you reach the save through \texttt{param\_object.set\_and\_save(...)}.
  \vfill
  Lookup is \textbf{O(N) over the table} --- linear scan over \texttt{var\_info[]}. Mitigable by caching pointers; pay the cost once at boot, not on the hot path.
\end{frame}

\begin{frame}{\texttt{AP\_Logger} --- recognition only here, M9 returns at applied}
  \begin{itemize}
    \item \citerange{libraries/AP\_Logger/AP\_Logger.h}{1}{80} --- public surface.
  \end{itemize}
  \vfill
  Logging is structured: each message type is registered via a \texttt{LogStructure} typedef and given a fixed binary layout. The vehicle code calls \texttt{logger.WriteV("ATT", ...)}; the binary message lands in the dataflash.
  \vfill
  M9 has the recognition-level tour of the on-disk log layout.
\end{frame}

\section{Module M6 --- Sensor Drivers (1.5 h, internals)}

\begin{frame}{Module M6 --- Sensor Drivers, Frontend/Backend, Airspeed}
  \textbf{1.5 h, lecture+code-walk, \emph{internals} depth.}\\[1ex]
  Why internals: airspeed is the plane-critical sensor and the frontend/backend pattern is the \emph{most reusable} design in ArduPilot.
  \vfill
  Learning objectives:
  \begin{enumerate}
    \item Read the frontend/backend pattern: \texttt{AP\_Airspeed} (frontend) $\rightarrow$ \texttt{AP\_Airspeed\_MS4525}, \texttt{AP\_Airspeed\_SITL} (backends). Same shape as \texttt{AP\_Baro}, \texttt{AP\_GPS}, \texttt{AP\_InertialSensor}.
    \item Read \texttt{AP\_Airspeed::get\_airspeed()} and the EAS$\leftrightarrow$TAS conversion.
    \item Recognise where airspeed feeds: TECS (M8), EKF3 wind estimation (M7), L1 only indirectly via EKF.
  \end{enumerate}
\end{frame}

\begin{frame}{The frontend/backend shape}
  \begin{itemize}
    \item \citerange{libraries/AP\_Airspeed/AP\_Airspeed.h}{1}{80} --- frontend: \texttt{get\_airspeed()}, \texttt{get\_airspeed\_ratio()}, \texttt{healthy()}, \texttt{use()}.
    \item \citerange{libraries/AP\_Airspeed/AP\_Airspeed\_Backend.h}{1}{80} --- backend interface: \texttt{init()} + \texttt{get\_differential\_pressure()}.
  \end{itemize}
  \vfill
  Frontend selects a backend per-instance from a \texttt{TYPE} parameter and owns the EAS$\leftrightarrow$TAS conversion, calibration, outlier-rejection logic.
  \vfill
  Two reference backends:
  \begin{itemize}
    \item \citerange{libraries/AP\_Airspeed/AP\_Airspeed\_SITL.cpp}{1}{80} --- canonical reference for any new backend (minimal, no platform deps).
    \item \citerange{libraries/AP\_Airspeed/AP\_Airspeed\_MS4525.cpp}{1}{100} --- reference for a real I\textsuperscript{2}C device.
  \end{itemize}
\end{frame}

\begin{frame}{Auto-calibration against GPS groundspeed}
  \begin{itemize}
    \item \citerange{libraries/AP\_Airspeed/Airspeed\_Calibration.cpp}{1}{80} --- the regression.
  \end{itemize}
  \vfill
  Basic idea: with no wind, airspeed equals groundspeed. So a regression of indicated airspeed against GPS groundspeed (gated on adequate variability) refines the airspeed sensor's calibration ratio.
  \vfill
  ArduPilot runs this online and writes the result back to \param{ARSPD\_RATIO}.
\end{frame}

\begin{frame}{Where airspeed lands downstream}
  \begin{itemize}
    \item \textbf{TECS} --- speed half of the energy balance (M8).
    \item \textbf{EKF3} --- wind-state observation when both airspeed and an alternative position source are valid (M7).
    \item \textbf{L1} --- \emph{not} consumed directly. L1 reads ground speed and bearing through AHRS.
  \end{itemize}
  \vfill
  This independence is part of why L1 is the cleanest extraction (Engineer 1's capstone).
\end{frame}

\section{Module M7 --- AHRS + EKF Internals (2.0 h, internals)}

\begin{frame}{Module M7 --- AHRS + EKF Internals}
  \textbf{2.0 h, lecture+code-walk+lab, \emph{internals} depth.}\\[1ex]
  This is where the audience leans in hardest. You have built EKFs. You want ArduPilot's specific design choices: lane-switch arbitration, error-score formula, wind-state inclusion, GPS source-set selection.
  \vfill
  Learning objectives:
  \begin{enumerate}
    \item Read \texttt{AP\_AHRS} as an interface; recognise that vehicle code never calls EKF directly.
    \item Read \texttt{NavEKF3::UpdateFilter} --- the periodic lane-arbitration loop with 10 s debounce, \texttt{coreBetterScore} test, \texttt{BETTER\_THRESH} constant.
    \item Read \texttt{NavEKF3::checkLaneSwitch} --- the explicit ``EKF failsafe is about to trigger; can a lane swap save us?'' entry.
    \item Read \texttt{NavEKF3\_core::errorScore} --- the consolidated metric: max of GPS / altimeter / airspeed / mag test ratios.
    \item Read \texttt{NavEKF3::switchLane} --- the actual switch with yaw/pos reset propagation.
  \end{enumerate}
\end{frame}

\begin{frame}{AHRS hides which estimator is running}
  Plane vehicle never calls \texttt{NavEKF3} directly. It calls \texttt{ahrs.update()}, \texttt{ahrs.get\_location()}, \texttt{ahrs.groundspeed\_vector()}, \texttt{ahrs.get\_yaw()}.
  \vfill
  \begin{itemize}
    \item \citerange{libraries/AP\_AHRS/AP\_AHRS.h}{1}{80} --- frontend declaration.
  \end{itemize}
  \vfill
  Active backend (EKF2, EKF3, External, DCM-only fallback) is selected at runtime. This indirection is what lets \texttt{AP\_L1\_Control} survive an estimator change.
\end{frame}

\begin{frame}{The lane-arbitration loop --- \texttt{NavEKF3::UpdateFilter}}
  \begin{itemize}
    \item \citerange{libraries/AP\_NavEKF3/AP\_NavEKF3.cpp}{910}{1020} --- the periodic body.
  \end{itemize}
  \vfill
  Structure:
  \begin{enumerate}
    \item Run all configured cores' state-and-covariance update.
    \item For each core, accumulate \texttt{errorScore} (consolidated test-ratio metric).
    \item Periodically (debounced to 10 s) compare cores. If a non-primary core's score is below the primary's by \texttt{BETTER\_THRESH}, switch the primary lane.
    \item On switch, propagate yaw and position resets so downstream consumers see a continuous state.
  \end{enumerate}
  \vfill
  Key call inside: \texttt{switchLane(newPrimaryIndex)} at line 1001.
\end{frame}

\begin{frame}{The explicit failsafe path --- \texttt{NavEKF3::checkLaneSwitch}}
  \begin{itemize}
    \item \citerange{libraries/AP\_NavEKF3/AP\_NavEKF3.cpp}{1029}{1062} --- the function.
  \end{itemize}
  \vfill
  Called from vehicle code when the EKF failsafe is about to trigger ``we are seconds from declaring no estimate.''
  \vfill
  Runs an immediate (debounce-bypass) lane comparison; switches if any non-primary core has a lower \texttt{errorScore} \emph{and} is below the absolute health gate.
  \vfill
  This is the path that saves the aircraft when GPS glitches inject a bad innovation into the primary lane. Lab L3 forces this path.
\end{frame}

\begin{frame}[allowframebreaks]{The actual switch --- \texttt{NavEKF3::switchLane}}
  \begin{itemize}
    \item \citerange{libraries/AP\_NavEKF3/AP\_NavEKF3.cpp}{1064}{1078} --- the body.
  \end{itemize}
  \vfill
  What it does:
  \begin{itemize}
    \item Stores the new primary index.
    \item Requests a yaw reset and a position reset to be propagated through AHRS so \texttt{ahrs.get\_location()} returns continuous values.
    \item Emits \texttt{GCS\_SEND\_TEXT} \texttt{"EKF3 lane switch \%u"}.
  \end{itemize}
  \vfill
  The yaw and position reset propagation is the subtle part --- without it, an L1 controller would see a step in cross-track error and command a sharp roll.
  \instnote{The \texttt{"EKF3 lane switch"} STATUSTEXT is exactly what L3 watches for. Cite \citeline{libraries/AP\_NavEKF3/AP\_NavEKF3.cpp}{1076} for the GCS\_SEND\_TEXT line.}
\end{frame}

\begin{frame}[fragile]{The error metric --- \texttt{NavEKF3\_core::errorScore} body}
  \begin{itemize}
    \item \citerange{libraries/AP\_NavEKF3/AP\_NavEKF3\_Outputs.cpp}{62}{86} --- function body.
  \end{itemize}
  \begin{Verbatim}[fontsize=\scriptsize,frame=single]
float NavEKF3_core::errorScore() const
{
    float score = 0.0f;
    if (tiltAlignComplete && yawAlignComplete) {
        // Check GPS fusion performance
        score = MAX(score, 0.5f * (velTestRatio + posTestRatio));
        // Check altimeter fusion performance
        score = MAX(score, hgtTestRatio);
        if (assume_zero_sideslip()) {
            const auto *arsp = dal.airspeed();
            if (arsp != nullptr && arsp->get_num_sensors() >= 2 &&
                (frontend->_affinity & EKF_AFFINITY_ARSP)) {
                score = MAX(score, 0.3f * tasTestRatio);
            }
        }
        if (frontend->_affinity & EKF_AFFINITY_MAG) {
            score = MAX(score, 0.3f * (magTestRatio.x + magTestRatio.y + magTestRatio.z));
        }
    }
    return score;
}
  \end{Verbatim}
\end{frame}

\begin{frame}{Reading \texttt{errorScore} aloud}
  Score starts at zero. Gated overall by \texttt{tiltAlignComplete \&\& yawAlignComplete} --- pre-alignment, the score stays at zero and the lane is not eligible for arbitration.
  \vfill
  Inside the gate, \texttt{MAX}-folded over four observation channels:
  \begin{itemize}
    \item \textbf{GPS} --- \texttt{0.5f * (velTestRatio + posTestRatio)}. Always evaluated.
    \item \textbf{Altimeter} --- \texttt{hgtTestRatio}, unit weight.
    \item \textbf{Airspeed} --- \texttt{0.3f * tasTestRatio}, gated on \texttt{assume\_zero\_sideslip()}, $\geq$ 2 airspeed sensors, and \texttt{EKF\_AFFINITY\_ARSP}.
    \item \textbf{Magnetometer} --- \texttt{0.3f * (mag.x + .y + .z)}, gated on \texttt{EKF\_AFFINITY\_MAG}.
  \end{itemize}
  \vfill
  Each test ratio is the squared-Mahalanobis innovation normalised by the gate; $\leq 1$ means innovation passed. A consolidated score above $\sim 1$ means at least one observation is rejecting consistently --- the lane is unhealthy.
\end{frame}

\begin{frame}[allowframebreaks]{The 0.3 scaling on airspeed and mag --- deliberate sensitivity reduction}
  Source comment is explicit: the EKF must be \emph{less reactive to airspeed innovations driven by gusts} than to GPS innovations.
  \vfill
  Gust-driven airspeed innovations would otherwise force false lane switches in cruise.
  \vfill
  Same 0.3 factor on the magnetometer term --- the magnetometer has its own independent switching mechanism that the affinity flag overrides.
  \instfaq{Why \texttt{MAX} and not \texttt{SUM}?}{Lane is unhealthy if any single observation channel is rejecting. \texttt{SUM} would mask a single bad channel behind several healthy ones.}
\end{frame}

\begin{frame}{The \texttt{EK3\_AFFINITY} parameter --- 2-min aside}
  \texttt{EKF\_AFFINITY\_*} flags are a per-observation-type opt-in, configured by \texttt{EK3\_AFFINITY}.
  \vfill
  Default \texttt{EK3\_AFFINITY = 0} disables both airspeed and mag terms. The consolidated score then collapses to:
  \begin{quote}
    \texttt{MAX(0.5f * (velTestRatio + posTestRatio), hgtTestRatio)}
  \end{quote}
  \vfill
  For a fixed-wing platform with redundant airspeed and magnetometers, enabling \texttt{EKF\_AFFINITY\_ARSP} and \texttt{EKF\_AFFINITY\_MAG} bits brings airspeed and mag into arbitration.
  \vfill
  This is exactly the detail Engineer 3's capstone has to confront when reimplementing the metric against a different sensor stack.
  \begin{itemize}
    \item Declaration: \citerange{libraries/AP\_NavEKF3/AP\_NavEKF3\_core.h}{140}{160}
    \item Per-tick aggregation \texttt{updateCoreErrorScores}: \citerange{libraries/AP\_NavEKF3/AP\_NavEKF3.cpp}{1092}{1099}
    \item Initial primary at boot \texttt{EK3\_PRIMARY}: \citerange{libraries/AP\_NavEKF3/AP\_NavEKF3.cpp}{715}{722}
  \end{itemize}
\end{frame}

\begin{frame}{Wind estimation --- structure not line-cite}
  Airspeed-fused wind state is part of the EKF3 core's state vector when both an airspeed sensor and an alternative position source are valid.
  \vfill
  Fusion code lives in \codepath{AP\_NavEKF3\_PosVelFusion.cpp} (the file is large; we walk the structure in narrative rather than line-cite).
  \vfill
  Compare to your stack:
  \begin{itemize}
    \item Some EKFs publish wind as a derived output of velocity differencing.
    \item ArduPilot models wind as part of the state, fused via airspeed innovations.
    \item The trade-off is observability vs degeneracy --- ArduPilot's choice is consistently the more honest one when an airspeed sensor is present.
  \end{itemize}
\end{frame}

\begin{frame}{Compare to your stack --- lane arbitration}
  Lane arbitration is the cross-cutting concern that varies most across proprietary EKFs.
  \vfill
  ArduPilot's choice:
  \begin{itemize}
    \item Single scalar consolidated \texttt{errorScore}.
    \item \texttt{MAX}-of-test-ratios.
    \item 10-second debounce on the periodic path.
    \item Debounce-bypass on the failsafe path.
  \end{itemize}
  \vfill
  Alternatives: per-axis health, vector-valued comparison, hysteresis on a different time constant. Comparable; the question is whether you can defend the choice in flight-test logs.
  \vfill
  Engineer 3's capstone in M11 lifts \emph{the arbitration logic only} into a stub repo. $\leq$ 50 lines of real algorithm.
\end{frame}

%------------------------------------------------------------------------------
\begin{frame}[allowframebreaks]{Adoption side-bar --- what comes with \texttt{AP\_NavEKF3}}

\section{Module M8 --- Control Pipeline (1.0 h, internals)}

\begin{frame}{Module M8 --- Control Pipeline: TECS, L1, APM\_Control, SRV\_Channels}
  \textbf{1.0 h, lecture+code-walk+lab, \emph{internals} depth.}\\[1ex]
  Why 1.0 h (vs 1.5 h slot in the requirements skeleton): the audience already knows PID + nav guidance. The unique-to-ArduPilot content fits in 1.0 h with Lab L4 inside.
  \vfill
  Learning objectives:
  \begin{enumerate}
    \item Read \texttt{AP\_TECS::update\_pitch\_throttle} --- entry point; energy-balance computation; \texttt{TECS\_SPDWEIGHT}.
    \item Read \texttt{AP\_L1\_Control::update\_waypoint} --- lateral-acceleration formula; the \texttt{0.3183099 = 1/$\pi$} damping.
    \item Read \texttt{AP\_RollController::get\_servo\_out} --- angle-error $\rightarrow$ desired-rate $\rightarrow$ PID, airspeed-scaled.
    \item Read \texttt{SRV\_Channels::push} and the cork/push pattern.
  \end{enumerate}
\end{frame}

\begin{frame}{TECS --- energy split as code}
  \begin{itemize}
    \item \citerange{libraries/AP\_TECS/AP\_TECS.cpp}{1270}{1350} --- \texttt{update\_pitch\_throttle} entry.
    \item \citerange{libraries/AP\_TECS/AP\_TECS.cpp}{678}{700} --- \texttt{\_update\_energies}.
    \item \citerange{libraries/AP\_TECS/AP\_TECS.cpp}{719}{820} --- \texttt{\_update\_throttle\_with\_airspeed}.
  \end{itemize}
  \vfill
  Canonical TECS split:
  \begin{itemize}
    \item Total specific energy: $STE = h + V^2/(2g)$
    \item Energy balance: $SEB = h - V^2/(2g)$
    \item Throttle commanded against $STE$.
    \item Pitch commanded against weighted blend of $STE$ and $SEB$.
  \end{itemize}
  \vfill
  Blend weight: \texttt{TECS\_SPDWEIGHT} at \citeline{libraries/AP\_TECS/AP\_TECS.cpp}{99}, default 1.0, range 0--2. 1 = canonical 50/50; 0 = ignore speed (good for glider final); 2 = ignore altitude (rare).
\end{frame}

\begin{frame}{The pitch damping gain we will perturb in L4}
  \begin{itemize}
    \item \citeline{libraries/AP\_TECS/AP\_TECS.cpp}{107} --- \texttt{TECS\_PTCH\_DAMP}, default 0.3.
  \end{itemize}
  \vfill
  L4 Phase B halves this to 0.15 to surface visible altitude-tracking oscillation.
\end{frame}

\begin{frame}{L1 --- lateral acceleration as code}
  \begin{itemize}
    \item \citerange{libraries/AP\_L1\_Control/AP\_L1\_Control.cpp}{206}{347} --- \texttt{update\_waypoint(prev\_WP, next\_WP, dist\_min)}.
    \item \citerange{libraries/AP\_L1\_Control/AP\_L1\_Control.cpp}{7}{44} --- the four \texttt{NAVL1\_*} parameters.
  \end{itemize}
  \vfill
  Computes the L1 reference vector; outputs \texttt{\_latAccDem} (lateral acceleration demand) plus \texttt{\_nav\_bearing} and \texttt{\_bearing\_error}.
  \vfill
  Damping factor: \texttt{0.3183099 = 1/$\pi$} applied as:
  \begin{quote}
    \texttt{\_L1\_dist = MAX(1/$\pi$ $\cdot$ damping $\cdot$ period $\cdot$ groundSpeed, dist\_min)}
  \end{quote}
  \vfill
  Body computes the line-of-sight angle Nu from velocity and reference vectors and converts to lateral acceleration.
\end{frame}

\begin{frame}{The four L1 parameters}
  \begin{itemize}
    \item \param{NAVL1\_PERIOD} --- default 17 s. The dominant tuning knob.
    \item \param{NAVL1\_DAMPING} --- default 0.75.
    \item \param{NAVL1\_XTRACK\_I} --- default 0.02.
    \item \param{NAVL1\_LIM\_BANK} --- default 0 (no extra bank limit beyond global aircraft limits).
  \end{itemize}
  \vfill
  Engineer 1's capstone extracts \texttt{AP\_L1\_Control} into a foreign-codebase stub. These four parameters and \texttt{update\_waypoint} are the public surface they take.
\end{frame}

\begin{frame}{Roll controller --- airspeed-scaled PID}
  \begin{itemize}
    \item \citerange{libraries/APM\_Control/AP\_RollController.cpp}{185}{227} --- \texttt{get\_servo\_out}.
  \end{itemize}
  \vfill
  Structure:
  \begin{itemize}
    \item Angle error (centi-degrees) $\rightarrow$ desired rate (deg/s) via time-constant $\tau$ = \param{RLL2SRV\_TCONST} (default 0.5 s) at \citeline{libraries/APM\_Control/AP\_RollController.cpp}{35}.
    \item $\rightarrow$ rate-PID call with \texttt{scaler} arg multiplying both proportional and feed-forward terms.
    \item \texttt{scaler} $= (V_{ref} / V_{current})^2$, computed by the caller.
  \end{itemize}
  \vfill
  The scaler makes the controller behave consistently across the airspeed envelope without re-tuning.
  \vfill
  L4 Phase A halves \param{RLL2SRV\_TCONST} from 0.5 to 0.25 to surface a faster-but-oscillatory roll response.
\end{frame}

\begin{frame}{The rate-PID parameters --- separate indices}
  \begin{itemize}
    \item \citerange{libraries/APM\_Control/AP\_RollController.cpp}{27}{50} --- \texttt{RLL2SRV\_TCONST}, \texttt{RLL2SRV\_RMAX}.
    \item \citerange{libraries/APM\_Control/AP\_RollController.cpp}{51}{100} --- the rate-PID block: \texttt{RLL\_RATE\_P}, \texttt{RLL\_RATE\_I}, \texttt{RLL\_RATE\_D}, \texttt{RLL\_RATE\_FF}.
  \end{itemize}
  \vfill
  These are a separate PID with its own indices --- distinct from \texttt{RLL2SRV\_*}.
  \vfill
  Naming pattern is consistent across pitch and yaw controllers in the same library.
\end{frame}

\begin{frame}{SRV\_Channels --- atomic output via cork/push}
  \begin{itemize}
    \item \citerange{libraries/SRV\_Channel/SRV\_Channels.cpp}{478}{510} --- \texttt{cork}/\texttt{push}.
    \item \citerange{libraries/SRV\_Channel/SRV\_Channel\_aux.cpp}{617}{680} --- \texttt{set\_output\_scaled}.
    \item \citerange{ArduPlane/servos.cpp}{861}{900} --- \texttt{Plane::set\_servos} call site.
  \end{itemize}
  \vfill
  Pattern:
  \begin{enumerate}
    \item \texttt{cork()} at the start of a control cycle --- latches all subsequent writes.
    \item Any number of \texttt{set\_output\_*} calls --- update internal channel buffers, do not push to hardware.
    \item \texttt{push()} at the end --- atomically writes all latched channels to RCOutput.
  \end{enumerate}
  \vfill
  ``All servos must move on the same tick edge.''
\end{frame}

\begin{frame}{Compare to your stack --- atomic servo update}
  Cork/push is one of several solutions:
  \begin{itemize}
    \item Double-buffered DMA on the RCOut driver itself.
    \item Dedicated transaction object passed into each setter.
    \item ArduPilot's stateful contract (you must \texttt{push} what you \texttt{cork}).
  \end{itemize}
  \vfill
  ArduPilot's choice keeps call sites simple at the cost of a stateful contract --- the cooperative scheduler makes the contract easy to honour.
  \vfill
  When you extract a controller, you do not need to bring cork/push --- write directly to your own actuator interface.
\end{frame}
