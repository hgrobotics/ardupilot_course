## Findings

### F1 — Quoted `errorScore()` body is fabricated; symbols and gating do not match the source
- **Severity**: blocker (citation-rigor)
- **Rubric**: [citation-rigor.md](../criteria/citation-rigor.md) — "Anchor existence", "Symbol naming"; the Forbidden clause "Cites that paraphrase symbol names".
- **Location**: M7, course lines 389-405 (the fenced `errorScore` code block immediately after the cite to [libraries/AP_NavEKF3/AP_NavEKF3_Outputs.cpp:62-83](../../libraries/AP_NavEKF3/AP_NavEKF3_Outputs.cpp#L62-L83)).
- **Observation**: The course presents a code block claimed to be the body of `NavEKF3_core::errorScore` and uses it as the centerpiece of the EKF internals walk for an audience that has built EKFs. The block is not what the source contains. Specific defects:
  - `gpsPosTestRatio` and `gpsVelTestRatio` are not symbols in the source. The actual GPS line is `score = MAX(score, 0.5f * (velTestRatio + posTestRatio));`. (`citation-rigor.md` Forbidden: "Cites that paraphrase symbol names".)
  - The airspeed gate in the course is `assume_zero_sideslip() && tasDataDelayed.allowFusion && (imuSampleTime_ms - lastTasPassTime_ms) > 100`. The actual gate is `assume_zero_sideslip()` and then `arsp != nullptr && arsp->get_num_sensors() >= 2 && (frontend->_affinity & EKF_AFFINITY_ARSP)`. None of `tasDataDelayed.allowFusion`, `imuSampleTime_ms`, or `lastTasPassTime_ms` appear in `errorScore()`'s gating.
  - The airspeed scaling factor in the course is implicit `1.0f * tasTestRatio` ("score = MAX(score, tasTestRatio)"). The actual factor is `0.3f * tasTestRatio`.
  - The magnetometer line in the course is `score = MAX(score, 0.5f * (magTestRatio.x + magTestRatio.y + magTestRatio.z));`. The actual line is `score = MAX(score, 0.3f * (magTestRatio.x + magTestRatio.y + magTestRatio.z));` and is gated by `(frontend->_affinity & EKF_AFFINITY_MAG)`, which the course omits.
  - The narrative paragraph following the block ("max of GPS fusion test ratios, altimeter test ratio, airspeed test ratio (only if the aircraft assumes zero sideslip and TAS data is fresh), and magnetometer test ratio") is *broadly* correct in shape, but the literal code is wrong, which is the worse of the two failure modes for an audience that came to read the math-as-code.
- **Evidence**: source confirmed by reading `libraries/AP_NavEKF3/AP_NavEKF3_Outputs.cpp:62-86`:
  ```
  62:float NavEKF3_core::errorScore() const
  63:{
  64:    float score = 0.0f;
  65:    if (tiltAlignComplete && yawAlignComplete) {
  66:        // Check GPS fusion performance
  67:        score = MAX(score, 0.5f * (velTestRatio + posTestRatio));
  68:        // Check altimeter fusion performance
  69:        score = MAX(score, hgtTestRatio);
  ...
  73:        if (assume_zero_sideslip()) {
  74:            const auto *arsp = dal.airspeed();
  75:            if (arsp != nullptr && arsp->get_num_sensors() >= 2 && (frontend->_affinity & EKF_AFFINITY_ARSP)) {
  76:                score = MAX(score, 0.3f * tasTestRatio);
  77:            }
  78:        }
  ...
  81:        if (frontend->_affinity & EKF_AFFINITY_MAG) {
  82:            score = MAX(score, 0.3f * (magTestRatio.x + magTestRatio.y + magTestRatio.z));
  83:        }
  84:    }
  85:    return score;
  86:}
  ```
- **Recommended fix**: replace the fenced block with the verbatim function body from `AP_NavEKF3_Outputs.cpp:62-86`. Then update the prose paragraph below to (a) correctly say the airspeed gate also requires `_affinity & EKF_AFFINITY_ARSP` and `>= 2` airspeed sensors, (b) note the magnetometer gate `_affinity & EKF_AFFINITY_MAG`, (c) state the scaling factors are 0.3f for both airspeed and magnetometer, and (d) flag for the audience that the EKF affinity flags are themselves a topic worth a 2-min aside since they control which observations participate in lane-switch arbitration. This is a senior-engineer audience; the affinity gating is the kind of detail they came to see.
